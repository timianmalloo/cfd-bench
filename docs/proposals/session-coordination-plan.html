Measured, not assumed

Where the coordination layer actually is

The pack ships a real coordination layer in coord-core.py — leases, artifact classes, seam requests, merge drivers, worktree lifecycle, and four metrics. I ran it against this repo rather than assuming its state.

The state is precise and slightly odd: the layer is half-live. Enforcement is on — the harnesses will refuse edits outside a session's boundary. Classification, session registration and the collaboration contract are all unconfigured. So today the layer can *stop* you without being able to *route* you, which is the least useful of the four possible states and the easiest to fix.

02

The finding that reorders everything

Contention is a property of the artifact

The instinct is to divide by task and give each session a lane. That is the wrong axis. The pack's own engine carries the counter-evidence in a comment beside the class registry:

“The class decides the MECHANISM entirely. Measured: the six busiest files in the reference repo are all generated, so a uniform lease aims at 13/60 and misses 58/60.”

In other words: most contention is not two people editing the same prose — it is two sessions regenerating the same derived file. A lease system aimed at authorship addresses a fifth of the problem. Classification addresses almost all of it, and needs no coordination at all.

ClassMerge mechanismCoordination needed
authored Conventional conflict markers — a human resolves Real. One owner per file, or a lease
derived merge-derived resolves to ours, records a regen owed, always returns 0; coord regen rebuilds it. A failed regen stays owed and reports non-zero, because a stale derived artifact looks finished None. Never merge what you can rebuild
register merge-register unions the append-only entries — always 0 None. Two sessions appending never conflict
hotspot Declared in CLASSES but no distinct mechanism is implemented Not usable yet — recorded so nobody plans around it

This repo's three worst contention points are all non-authored files that are currently classified authored:

  • docs/docs-index.js — derived. Regenerated by docs-graph.py derive. Every session that adds a knowledge artifact rewrites the whole file. Two sessions doing so guarantees a conflict, and resolving it by hand is both pointless and error-prone.
  • docs/audit/audit-log.jsonl and change-log.jsonl — register. Append-only by design. Every session appends on every substantive turn. Union-merge is exactly right and hand-resolution is exactly wrong.
  • docs/audit/audit-data.js — derived projection of the JSONL.

Those four files are the ones this session touched on every single commit. In a two-session world they would conflict on essentially every merge, and each conflict would be a human resolving a machine-generated file by hand — the worst kind of work.

03

Do this first

Twenty lines that remove most of the problem

The registry format is pattern: class [command], one per line, # for comments — a deliberately line-oriented parser, not general YAML. Longest matching pattern wins; a derived entry must carry a regenerate command, because a derived class with no command would resolve every merge and leave the artifact permanently stale while claiming to be handled.

# .agents/artifacts.yml — what each artifact IS decides how it merges.
# Written 2026-09-06. Format: pattern: class [regenerate command]

# --- derived: never merge, always rebuild ---
docs/docs-index.js:        derived   python docs/ai-forward-pack/scripts/docs-graph.py derive
docs/audit/audit-data.js:  derived   python docs/ai-forward-pack/scripts/audit-log.py render

# --- register: append-only, union-merge ---
docs/audit/audit-log.jsonl:   register
docs/audit/change-log.jsonl:  register
docs/health-history.jsonl:    register

# --- everything else stays `authored` by default. Do not enumerate it.        ---
# NOTE: docs/audit/audit-log.md is AUTHORED prose about the logs, not a
# projection of them — deliberately absent so it keeps conflict markers.

Both regenerate commands are Verified, and one of them caught an error. docs-graph.py derive rebuilds docs-index.js — run a dozen times this session. For the audit projection I first wrote audit-log.py regen from inference; there is no such subcommand — the real one is render ("Regenerate audit-data.js from the JSONL and ensure the viewer exists"). Checking it also showed that audit-log.md is authored prose about the logs, not a projection of them, so it stays out of the registry.

That near-miss is the argument for the rule. A wrong regenerate command is worse than no entry: the merge resolves silently and the artifact goes permanently stale while claiming to be handled. Verify every command in this file by running it.

Then declare the driver and install the boundary hook:

python docs/ai-forward-pack/scripts/coord-core.py install
python docs/ai-forward-pack/scripts/coord-core.py doctor   # expect: registry present, driver declared

Cost: about twenty lines and one command. Benefit: the four files this project touches on every commit stop being conflict sources entirely. Nothing else in this proposal comes close to that ratio, which is why it is section 03 and not an appendix.

04

The division

Five tracks, one-way dependencies

With derived and register files handled mechanically, what remains is authored code — and there the rule is simple: one owner per file, and make every dependency one-way. A dependency graph that is a DAG needs far less coordination than one with cycles, because the downstream side rebases and the upstream side never has to ask.

TrackOwns (authored)Depends onContention risk
A · Core Geometry model, section catalog, estimator, VLM tier Spine only Low nothing upstream of it
B · Surface WPF shell, ScottPlot charts, curve editors, HelixToolkit viewport A's interfaces, not its internals Medium the seam is the risk, not the files
C · Solver De-risk slice, ICfdBackend, case generation, CUDA kernels Spine only (geometry types) Very low separate project, separate toolchain
D · AI Numeral check, explain, brief→intent, evals A's results, read-only Very low additive by COMMIT-04
E · Knowledge docs/ — ADRs, the units spec, expert reviews Nothing Low once registered its only overlap is the derived index and the registers

Track E is the one that looks free and is not. Documentation work touches docs-index.js and both audit registers on every commit — which is precisely why section 03 comes first. Unregistered, E collides with everything. Registered, it collides with nothing.

05

The protocol

What a session actually does

Open

coord worktree new --branch <work-name> --session <id>. Branch named for the work, not the session (WT5). One session per tree, one tree per session (WT3). A new task means a new session even in the same tree (WT1a) — a worktree isolates the tree, nothing isolates the context.

WT1, WT3, WT5
Claim

coord claim --wi <work-item> --path <path> [--ttl] before writing an authored file outside your track's ownership. coord check answers "may this session touch this path?". Derived and register files need no claim — that is the whole point of classifying them.

TTL'd
Compose

Do not share files — share requests. When B needs an interface change from A, coord request add records a seam request; A resolves it on its own cadence with coord request resolve. Neither session blocks, and the seam is recorded rather than negotiated in a merge.

the key primitive
Commit

The pre-commit hook is the universal floor: it refuses unclaimed staged paths. coord guard refuses to move HEAD over work held in one place. Both are already enforcing for Claude Code and Copilot.

enforcing
Close

coord release, then coord worktree cleanup — which reports by default and deletes only with --remove. A tree is removable only when it is not primary, not your cwd, clean including untracked, holds no commit that exists nowhere else, and is unheld. Anything else is reported, never removed, and the tool prints every refusal with its reason (WT7, WT8, WT12).

WT6–WT12

Never remove a worktree to resolve a conflict (WT11). If two sessions have collided, deleting one side destroys the evidence of what collided. Resolve in the tree, then release.

06

The serial spine

What must not be parallel

GO5's independence test requires all three of: no data edge, no decision edge, and no shared exclusive resource. The middle one is the binding constraint here, and it produces a hard sequencing rule:

Until the interfaces are fixed, every track's result changes every other track's shape. That fails GO5(b) outright. The spine — units and coordinate conventions, the geometry model, the file format, and the interface signatures between layers — must be authored serially, in one session, before any track forks.

Three more things stay serial for the same reason:

  • Any change to the geometry model schema. It is the shared vocabulary; a change to it invalidates in-flight work in every track. Route it through a seam request, and let the spine owner make it.
  • Two sessions in the same layer. Not forbidden by the tooling, but it fails the coupling test — tightly-coupled work is cheaper and more reliable in one coherent session.
  • The first commit after the class registry lands. Verify the driver is effective (coord doctor) before two sessions rely on it, or the first merge will quietly conflict anyway.
07

The honest part

Parallelism is probably not the prize

You asked to optimise for parallelism. The evidence in the pack argues for tempering that, and it would be a poor proposal that didn't say so.

GO6 is blunt about it: parallelism is a cost multiplier, not a saving, when branches are separate explorations — the production orchestrator-worker shape reports roughly 15× token usage, justified only for open-ended, breadth-first, loosely-coupled work. Pay the multiplier deliberately or not at all.

And this is a one-person project. Two concurrent sessions do not halve the calendar for a solo developer; they add context-switching cost, and each session re-reads its own context on every request.

So what do worktrees actually buy here? Three things, and none of them is speed:

  1. Isolation. The de-risking slice (Track C) hand-builds a mesh and runs a solver. That should not touch the tree where the application is being written. WT2 exists exactly for this.
  2. Long-running work. A CFD run takes hours. A worktree lets it own a tree while you keep working elsewhere — the clearest genuine parallelism in the whole project, because the waiting is machine time, not yours.
  3. Context hygiene. WT1a's measured shape is a 23-hour session growing from 159k to 564k tokens across three unrelated tasks with zero compactions, because a long-context tier never forces one. Class CTX-A. A new task in a new session is worth more than a new tree.

Where parallelism does become real is if you run agents concurrently — Track C's solver work and Track E's documentation genuinely can proceed while you are in Track A. That is the case the tracks above are designed for, and the artifact registry is what makes it cheap. But it is a decision to make deliberately, with the 15× multiplier in view, rather than a default.

Order of operations

What to do, and what it costs

#ActionCostWhy now
1Write .agents/artifacts.yml; verify the regen commands; run coord install and coord doctor ~30 min Removes the four files that conflict on every commit. Best ratio in the plan, and it is needed even for one session
