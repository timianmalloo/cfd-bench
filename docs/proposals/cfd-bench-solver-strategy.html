01

The finding that reframes the brief

This is two problems, not one

The brief asks for one simpler solution covering hydrofoils and surfboards. The literature does not treat these as one problem, and the split is structural rather than a matter of degree.

Submerged foil solved cheaply

Attached flow over a lifting surface at high Reynolds number. Potential-flow methods — lifting line, vortex lattice, panel — mesh only the surface and append viscous drag from 2D sectional polars.

Cost: around 1% of an equivalent RANS solution. This is what XFLR5 and Typhoon already do, for free.

Planing board genuinely hard

Free-surface, partially-wetted, dynamically trimming. Potential flow does not apply at all. Wetted area changes with speed and attitude, so trim and sinkage are solved outputs, not inputs.

Cost: Savitsky's algebra in microseconds, or RANS+VOF with 6-DOF motion in hours.

One application spanning both is reasonable. One solver spanning both is the primary design failure mode available here, and every option below is judged partly on whether it avoids it.

What this laptop can actually hold

Two caveats on those numbers, stated plainly. The throughput figure is scaled by memory bandwidth from a published desktop RTX 5090 benchmark — this laptop has exactly half the bandwidth, and its 175 W power cap is not in the model. Nothing here has been measured on this machine. Second, a uniform grid has no adaptive refinement: widening the domain to capture surface waves or a whole board re-prices the entire box at the finest cell size.

05

The decision

Four options

OPTION A

Low-order only — panel/VLM foil tool plus Savitsky planing

Pure C# on the CPU. Vortex-lattice or panel solver for the foil with XFOIL-style sectional polars; Savitsky's algebra for the board. WPF front end. No CUDA, no GPU, no toolkit install.

For

  • Ships in weeks, not quarters. Entirely within known .NET territory.
  • Interactive by construction — every evaluation is sub-second.
  • Zero dependency risk. No Blackwell question, no licence question.
  • Both halves of the brief get an answer.

Against

  • Largely duplicates XFLR5 and Typhoon, which are free and mature.
  • No free surface at all — cannot see submergence effects or ventilation.
  • Linear methods: stall is not represented, so the tool must actively refuse to answer outside its envelope.
  • Leaves the RTX 5090 completely idle.
OPTION B

Two tiers — low-order core, GPU LBM for what it cannot see

Recommended

Option A as the daily-use tier, plus a CUDA LBM solver for free-surface, separated and planing cases. Kernels in C++/CUDA compiled to sm_120, called from C# across a thin P/Invoke boundary; WPF shell with D3D interop for live field visualisation.

For

  • Targets the actual gap: no existing small tool models the water surface, and hydrofoils run shallow where that dominates.
  • The fast tier answers design questions; the slow tier validates it. Each checks the other.
  • Uses the hardware that makes this machine interesting, at a size it comfortably fits.
  • Native CUDA sidesteps every ILGPU uncertainty and gives full sm_120 access.

Against

  • Largest scope. Two solvers, two validation obligations.
  • Introduces a native interop boundary — build complexity, marshalling, debugging across the managed/unmanaged line.
  • LBM accuracy above Re 106 is unproven for this use and must be demonstrated, not assumed.
  • Requires the CUDA Toolkit and a working MSVC host-compiler chain.
OPTION C

Wrap what exists — build only the experience

Treat FluidX3D or OpenFOAM as the engine. Spend all effort on a WPF application that drives them: geometry, case setup, run management, visualisation, comparison.

For

  • Real, validated physics on day one. No solver to write or defend.
  • FluidX3D is the fastest LBM implementation available — you will not beat it by hand.
  • The genuine pain in CFD is setup and post-processing, which is exactly what this option attacks.

Against

  • FluidX3D is non-commercial only — a hard ceiling if this is ever sold.
  • You own none of the physics, so you cannot fix what it gets wrong.
  • OpenFOAM's setup burden is relocated, not removed; interFoam free-surface artefacts become your artefacts.
  • No interactivity — these are batch solvers, not something to scrub a slider against.
OPTION D

Single-language GPU — ILGPU end to end

One C# codebase. ILGPU JIT-compiles kernels to PTX, so there is no native project, no P/Invoke, and no CUDA Toolkit dependency.

For

  • Architecturally the cleanest: one language, one build, one debugger.
  • No toolkit install; driver-level PTX JIT only.
  • Permissive NCSA licence.

Against

  • ILGPU v1.5.3 shipped in July 2024, before Blackwell. sm_120 support is undocumented and unverified — this may simply not run.
  • Release cadence suggests limited maintenance against new architectures.
  • Kernel-language restrictions constrain how the solver can be written.
  • Peak bandwidth utilisation — the only thing that matters for LBM — is unproven here.

Recommendation: Option B, built in the order of Option A. The two-tier architecture is the only one that reaches the real gap, but its low-order tier is also a complete, useful product on its own. Build that first and the project has value in weeks regardless of whether the LBM tier ever proves accurate enough. That sequencing turns the largest-scope option into the lowest-risk one.

06

Sequencing

What to do, in what order

Phase 02–3 days

Answer the three questions that could invalidate the plan. Install CUDA Toolkit 12.8+ and compile a trivial sm_120 kernel. Run the FluidX3D benchmark to replace the estimated 9,570 MLUPs/s with a measurement. Read Typhoon's source to find out what method it uses — it may already answer the foil half.

Cheap, and each one can change the architecture. None should be assumed.

Phase 1the product

The low-order tier, end to end. Foil geometry in, sectional polars, vortex-lattice 3D solve, craft equilibrium for trim and ride height, Savitsky for the board. WPF interface with live parameter response. Salt and fresh water as an ITTC-sourced fluid record — two constants, one code path.

Ends with something usable every day. The validity envelope is enforced by the tool, not documented in a footnote.

Phase 2the differentiator

The CUDA LBM tier, validated before it is trusted. The first deliverable is not a solver but a comparison: a NACA section at a Reynolds number with published experimental polars, computed lift and drag set against them. Free surface and submergence effects follow only once that comparison holds.

If drag proves unreliable at this Reynolds range while lift holds up, that is a real finding and the tool says so on screen — it does not quietly report both as equal.

Laterif earned

Shape optimisation via adjoints, or a learned surrogate over accumulated solver output. Both are accelerators over a working solver and cannot precede one — a surrogate needs a training corpus that only Phase 2 can produce.

07

The case against

The strongest argument for not building this

XFLR5 is free, mature, and already couples XFOIL viscous polars to 3D panel methods. Typhoon is free, open source, and already solves whole-craft hydrofoil equilibrium with stability eigenvalues. FluidX3D is the fastest LBM implementation in existence — nothing hand-written on one laptop will beat 19,141 MLUPs/s at 55 bytes per cell. Savitsky's planing equations fit on one page and have sixty years of practitioner trust. Every component of this brief already has a free, better-validated solution.

This argument substantially survives, and it should shape the scope rather than be waved away. The evidence does not support building a general CFD package, and it does not support hand-writing a faster LBM kernel. Both would lose.

What it does not defeat is a narrower claim, which is the one this proposal rests on:

  • No small tool models the free surface. Hydrofoils operate at shallow submergence where lift falls off with depth and ventilation can collapse it outright. XFLR5 and Typhoon cannot see this at all — a first-order effect, invisible to the whole category.
  • No small tool handles a planing board. That is Savitsky or RANS+VOF, and neither is in the foil-design tools.
  • Nothing joins the workflow. Design the foil, solve the craft equilibrium, watch the flow, compare against the board — in one Windows application, on local hardware.

So the defensible project is an integrated application over largely established methods, not a novel solver. If that framing is wrong, the plan above is wrong with it, and Phase 0 is where that surfaces cheaply.
