01

The rule

One sentence that governs everything

The model reads and writes language. The solver reads and writes numbers. Numbers flow into the model as context; they never flow out of it as results.

Every capability below is judged against that sentence. It exists because a CFD tool is about as deterministic a path as software gets: a user who cannot reproduce a number cannot trust the tool, and a number that came from a language model is not reproducible. The project's own AI review lens holds a hard veto on exactly this — non-determinism leaking into a deterministic path.

The useful thing about the rule is that it is mechanically checkable. Every numeral appearing in model-generated text must also appear in the structured input given to that call. That is a unit test, not a guideline — roughly twenty lines of code guarding the single most damaging failure this feature set can produce.

Where it earns its place

Seven capabilities, ranked

Ranked by value over risk. Your two ideas are the top two — they are the best on the list, and for the same underlying reason: in both, the model is handling language about facts it was handed.

Brief → structured design intent. Prose in, typed constraints, objectives and context out. Structured outputs guarantee the shape, so the only possible failure is a wrong value — and the user confirms before the optimiser runs. incl.

The hard constraint on B, and it is the whole ballgame. Every number in an explanation must be a number that was passed in. The moment the model writes “L/D is around 19” instead of reading 19.8 from the solver, it has fabricated engineering data with total confidence and no visible tell. That is why the numeral check is non-negotiable rather than nice-to-have.

The other half of the answer

Where it must not go

04

The gate

Every capability ships with an eval

The project's AI review lens holds a hard veto on an AI capability with no eval harness. So each of these ships with one, or does not ship.

CapabilityEval setGrading
Brief → intent Briefs with hand-written expected intents, including adversarial ones — vague, contradictory, over-constrained Exact match on numeric constraints, semantic on objectives, plus a precision check: did it invent a field?
Explain Design/result pairs with known correct readings (1) Numeral check — mechanical, automatic fail. (2) No unsupported claims. (3) Human usefulness rating
Diagnose Genuinely failed runs with known root causes Did it name the actual cause? Did the suggested fix work when applied?
KB Q&A Questions with known answers, plus questions whose answers are not in the base Correctness on the first set; refusal on the second. Confident answers to unanswerable questions are the failure mode
Vocabulary bridge Rider phrases with expert-labelled meanings Agreement with the expert label

The numeral check is the one to build first. It is a deterministic guard on a non-deterministic component, it is trivial to write, and it catches the failure that would do the most damage. It also has an open question attached — rounding, unit conversion and derived quantities all produce numerals not literally present in the input, so it will need a tuning pass to allow rounding of supplied values while still rejecting unsupplied ones.

05

Cost

Cheaper than it feels

Claude Opus 5 at $5 / $25 per million tokens in/out. Every figure in section 02 is computed from that, not estimated.

Caching pays for itself after 1.4 calls. The 15k-token knowledge prefix costs $0.075 fresh against $0.0075 on a cache read — a 10× difference — against a one-time write of $0.094. Verify it is actually working by watching Usage.CacheReadInputTokens; if that is zero across repeated calls, something in the prefix is varying and the saving is imaginary.

A note on model choice: the bounded capabilities — vocabulary bridge, intent extraction — might run acceptably on a cheaper model. That is a legitimate option and it is your call, not mine. But it should be measured against the eval rather than assumed, which is another reason to build the evals first.

06

The awkward part

You cannot ship a key in the binary

You mentioned including a Claude API key in the solution. A key inside a desktop binary is extractable — it has to be present at runtime, so it can be recovered, and obfuscation only changes how long that takes. Three honest options:

ApproachVerdict
BYOK — you supply your own key Right for this project Non-commercial, single user, no distribution problem. Key lives in the Windows credential store or an environment variable — never in the repo, never in the binary
A proxy service holding the key server-side Only for distribution The correct answer for shipped commercial software. Adds infrastructure, auth and a bill
Key embedded in the app Not an option It leaks, and the leak bills you

For a tool you run on your own machine, BYOK is not a compromise — it is the correct design. It also makes the offline requirement fall out naturally: no key configured, no AI features, everything else works exactly as before.

07

Integration

What this looks like in C#

The official SDK is Anthropic on NuGet, which drops into a WPF application directly. The pieces that matter for these capabilities:

// Brief -> structured intent. The schema is the guarantee:
// the model cannot return a malformed object, only a wrong value.
var response = await client.Messages.Create(new MessageCreateParams
{
    Model      = "claude-opus-5",
    MaxTokens  = 16000,
    OutputConfig = new OutputConfig
    {
        Format = new JsonOutputFormat { Schema = designIntentSchema },
    },
    // The knowledge prefix is stable -> cache it. 10x cheaper on reads.
    System = new List<TextBlockParam>
    {
        new() { Text = knowledgeBasePrefix,
                CacheControl = new CacheControlEphemeral() },
    },
    Messages = [ new() { Role = Role.User, Content = brief } ],
});

// Always verify the cache is real, not imagined:
// response.Usage.CacheReadInputTokens == 0 across repeats means
// something in the prefix is varying.
  • Client: AnthropicClient client = new(); reads ANTHROPIC_API_KEY, or set ApiKey from the credential store.
  • Thinking is on by default on Opus 5; Effort nests under OutputConfig, not top level.
  • Stream anything long-form — explain, report — so the UI shows progress rather than a pause.
  • Catch a most-specific-first exception chain from Anthropic.Exceptions, so retryable (429, 5xx) and non-retryable (400, 404) are distinguishable rather than collapsed.
  • Assistant prefill is not supported on Opus 5 — structured outputs are how you control format.
08

Risks

Five ways this goes wrong

  1. Fabricated numbers, presented with total confidence. The dominant risk. Mitigated by the numeral check — and by rendering model-generated text visually distinctly from computed values, so the eye can tell them apart.
  2. Authority laundering. An eloquent explanation makes a result feel more validated than it is. A fluent paragraph about an estimator-tier number can read as an engineering endorsement. Explanations must inherit and display the confidence of the tier they describe — an explanation of a surrogate result should look less certain than one of a CFD result.
  3. Prompt injection through solver logs and files. Diagnosis reads machine output; import reads files. Neither is fully trusted. Keep model output confined to advice; never let it trigger an action directly.
  4. Silent scope creep into computation. The pressure to let the model “just estimate” something when a tier is slow will be constant and reasonable-sounding. The rule in section 01 exists to be enforced, not admired.
  5. Non-reproducible explanations. The same design may be explained differently on two runs. Fine for prose, unacceptable for numbers — which is precisely the line the rule draws.

Where I'd start. Build capability B (explain) first, because it is your highest-value idea and it forces the numeral check into existence. The check is the guard rail everything else leans on, and building the feature that most needs it first means the guard rail is real before the riskier capabilities arrive.
