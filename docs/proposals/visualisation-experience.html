The chart set

Six that diagnose, six that are foil-specific

Standard airfoil post-processing has a settled core. The second tier is where a hydrofoil tool earns its keep, because generic aerodynamic tools do not carry it.

Two rules for every chart in the set. Overlay is mandatory — comparing two candidate sections is the actual task, and a chart that cannot overlay is half a chart. And every ranked view must be Reynolds-parameterised, because Phase 0 measured the section ranking flipping between Re 6×10⁵ and 10⁶. A “best sections” list with no Reynolds number on it is misinformation.

02

The correction most tools skip

A 2D section at a spanwise station

The request was a 2D view of a section “expressed as distance from mid point”. That has a proper method behind it — quasi-3D strip theory — and getting it wrong produces a picture that looks right and is not.

The established chain: a vortex lattice method computes spanwise loading, then strip theory applies 2D analysis at spanwise stations. The wing is treated as a sum of section strips, and the 3D effect is the downwash from the trailing vortex sheet, producing a local induced angle of attack that modifies sectional lift.

An architectural advantage worth naming. Unlike most CFD, where visualisation happens after computation, GPU-based rendering allows real-time visualisation while the computation runs. Since the LBM tier already holds the field in VRAM, rendering from the same buffers via D3D interop avoids a readback entirely — a concrete reason to keep the solver in CUDA and the viewport in SharpDX rather than splitting them.

04

The stack

And the gap where VTK should be

VTK and ParaView have bindings for C++, Python, Tcl/Tk, Java and JavaScript. C# and .NET are not among them. The default scientific-visualisation stack is simply unavailable to a WPF application. This is a real finding, not a gap in the search, and it shapes the whole approach.

Three ways forward:

  1. Render it ourselves in HelixToolkit / SharpDX. Full control, no interop, and — the deciding point — the CAD editor needs this viewport anyway, so it is not an additional dependency. Streamline integration and LIC are both implementable as compute and pixel shaders. Recommended.
  2. Shell out to ParaView for anything exotic, accepting a separate window. A pragmatic escape hatch, not an interactive experience.
  3. Python sidecar with VTK, piping images back. Adds a Python runtime to a .NET product for one feature.

The scope discipline that makes (1) safe: do not build a general visualisation toolkit. Build the six views this domain needs. A general toolkit is how this becomes a two-year project.

2D charts — ScottPlot

Free, open source, interactive, built for large datasets, WPF among many targets. Comparisons place it ahead of OxyPlot and LiveCharts2 for large static datasets; LiveCharts2 is the most modern-feeling with MVVM binding and animation, OxyPlot has the broadest reach. Our charts are dense — a Cp distribution is hundreds of points, a polar sweep thousands — and static per frame, so performance at scale is the deciding axis and animation polish is not.

Video — FFMpegCore

FFMpegCore 5.4.0 writes video frames directly from program memory via IPipeSource / RawVideoPipeSource, with no intermediate PNGs — which matters when a sweep is hundreds of frames. FFMediaToolkit and NReco VideoConverter are the alternatives. Render each sweep step to an offscreen target and pipe it straight out.

05

The unifying idea

The sweep is a domain object, not a UI loop

The request was for both 2D and 3D views to sweep angle of attack and velocity, and to export as video. Treating the sweep as a first-class object rather than an animation loop collapses four features into one:

sweep {
  variable   alpha            // or velocity | station | reynolds
  from       -2deg  to  12deg
  steps      57
  hold       speed=16kn  depth=0.45m  fluid=seawater@15C
}
  • Every view binds to the same sweep, so scrubbing moves the charts, the 2D section and the 3D field together.
  • The sweep is the video timeline. Export becomes “render this sweep to frames”, not a separate export mode with its own settings.
  • A sweep is exactly what a polar is. The polar chart and the animation are two views of one computation — compute once, present twice.
  • Cacheable and re-orderable. At estimator cost the whole sweep precomputes instantly; at CFD cost it becomes a job queue with the same interface.

One consequence worth planning for: because a sweep at the estimator tier is instantaneous and at the CFD tier takes hours, the same UI must gracefully represent both. That argues for the sweep carrying its fidelity and its completion state, so a partially computed sweep is a first-class thing the charts can draw.

06

Honest limits

What not to draw

  • Do not draw a separation marker the model cannot support. The closed-form estimator has no separation model at all. NeuralFoil gives transition and boundary-layer parameters but not a separation point. Showing separation honestly requires at least the VLM+strip tier — and a confidently drawn marker with nothing behind it is worse than omitting it.
  • Slicing an LBM field for the 2D view is not free. A uniform Cartesian lattice does not align with a swept, twisted station plane, so interpolation is required — and its accuracy is worst near the surface, which is exactly where it matters.
  • Colour maps need deciding deliberately. The default rainbow map is known-poor for scalar fields; a perceptually uniform map should be the default. No source was consulted on this and it should be before the first Cp contour is drawn.
  • Every displayed number inherits its tier's confidence. A Cp curve from the surrogate and one from OpenFOAM should not look identical on screen.

Evidence: docs/knowledge/flow-visualization/ — XFOIL analysis outputs, NASA post-stall airfoil database, quasi-3D strip theory coupling, LIC and GPUFLIC, ScottPlot/OxyPlot/LiveCharts2 comparison, ParaView language bindings, FFMpegCore.

Load-bearing finding: there is no VTK binding for .NET. The recommendation to render in HelixToolkit follows from that, and is only safe if the scope stays at six views rather than a general toolkit.
